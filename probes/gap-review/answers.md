# 빈틈 검토 시험 — 정답표 (검토자에게 주지 않는다)

`case/`에 일부러 심어 둔 빈틈 10개다. 검토 보고가 같은 문제를 짚었으면 찾은 것으로 센다(표현이 달라도 된다). 심각도는 채점용이다.

| # | 빈틈 | 어디 | 종류(REVIEWER.md 문항) | 심각도 |
|---|---|---|---|---|
| 1 | 무엇을 잠그는지 없다(계정인지, IP인지, 둘의 조합인지) | SPEC 완료 기준 | 정의되지 않은 말(2) | 높음 |
| 2 | 해제 방식이 어긋난다: "10분 뒤 자동으로 풀린다" 대 "관리자가 해제할 때까지" | SPEC 완료 기준 대 사용자 흐름 | 모순(4) | 높음 |
| 3 | 실패 횟수가 언제 0으로 돌아가는지 없다(성공하면, 시간이 지나면) | SPEC 전체 | 빠진 것(4), 물어야 할 질문(3) | 높음 |
| 4 | 횟수가 다르다: 스펙·요구 원문은 5회, 인계의 인수 조건은 3회 | SPEC 대 T01 인수 조건 | 모순(4) | 높음 |
| 5 | `verifyPassword`가 true/false를 돌려준다고 적었지만 코드는 `{ ok, reason }` 객체를 돌려준다 | SPEC 제약 대 src/auth.js | 가리킨 코드와 맞지 않음(4) | 중간 |
| 6 | "기존 rate limiter 모듈"이 주어진 코드에 없다(경로도 없다) | SPEC 제약 | 전제된 지식·경로 부족(2) | 중간 |
| 7 | "잠금이 안전하게 동작한다"는 실행해서 확인할 수 없다 | SPEC 완료 기준 | 확인할 수 없는 완료 기준(5) | 중간 |
| 8 | "운영 로그에 잠금 이벤트가 남는다"에 검증 방법이 없고 `verify` 명령이 덮지 않는다. 로그가 무엇인지도 없다 | T01 인수 조건 | 확인할 수 없는 인수 조건(5) | 중간 |
| 9 | 인계가 관리자 해제 화면을 요구하지만 스펙은 관리자 화면을 하지 않는다고 했다 | T01 인수 조건 대 SPEC 하지 않을 것 | 요구보다 과한 것·모순(4) | 높음 |
| 10 | 인증을 바꾸는 작업인데 `review: normal`이다 | T01 머리말 | review 등급이 위험에 맞지 않음(5) | 중간 |

## 채점
- 찾은 수 / 10, 그 가운데 정답 `높음` 5개 중 실제로 `높음`으로 판정한 수(심각도를 낮춰 적었거나 `중간` 항목을 3개 이상 `높음`으로 과잉 격상했는지도 따로 적는다).
- 틀린 지적 수: 문서나 코드에 근거가 없는 지적. 정답표에 없더라도 근거가 맞으면 "추가로 맞는 지적"으로 따로 센다(감점하지 않는다).
- 판정 줄: 높음이 하나라도 있으므로 `진행 가능`이면 틀린 판정이다.
- 함께 적는다: 걸린 시간, 띄운 쪽이 처리한 승인 창 수, 보고 형식(첫 줄 형식, 근거·심각도·확신, 읽은 파일 목록)을 지켰는지.
